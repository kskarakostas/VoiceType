# VoiceType 3.0 L3 Site rules Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Per-site rules: hide the idle pill on a site and give a site its own mode, edited from the pill, the popup and a Sites page.

**Architecture:** Pure rules live in `src/shared/sites.js`. The service worker alone reads `siteRules`: it resolves the sender's top-level URL with `ruleFor` and hands a content script only `site: { hidePill, mode }`, in `GET_SETTINGS` and in a per-tab `SETTINGS_CHANGED`. The recorder fixes the mode at start from that rule. Two new messages write rules: `SET_SITE_MODE` (content, host taken from the sender) and `SET_SITE_RULE` (extension pages only). A hidden site shows today's pill only while recording, processing or showing a status; L5 replaces that presentation with Minimal.

**Tech Stack:** Chrome MV3 (minimum Chrome 140), plain JavaScript with JSDoc, esbuild, Vitest with jsdom, Playwright with bundled Chromium.

**Spec:** `docs/superpowers/specs/2026-11-03-v3-design.md` (sections 2 V3, V7 to V10; 3; 5; 6.4). Master plan: `docs/superpowers/plans/2026-11-03-v3-master.md` (L3 row and the note under the table). Previous lanes: the L0 ledger (deferred for L3: `siteKey` guards), the L1 ledger (deferred for L3: `controller.js` JSDoc), the L2 ledger. Decisions and Step A evidence: `docs/superpowers/plans/2026-11-03-v3-l3-ledger.md`.

## Global Constraints

- `minimum_chrome_version` stays `"140"`; no new permissions; zero runtime dependencies.
- `SETTINGS_VERSION`, migration routing and `repairSiteRules` are untouched (L0 only). `toPublicSettings` keeps excluding `keys`, `siteRules` and `dictionary`.
- `UPDATE_SETTINGS` and `CONTENT_PATCH_FIELDS` stay unchanged. New message names go in `src/shared/messages.js` only (append). `ACCESS` gains `SET_SITE_MODE: ['content']` and `SET_SITE_RULE: ['extension']`.
- `siteRules` is never sent to a content script. A content script can never name a host.
- Site rules are written only through `SET_SITE_MODE` and `SET_SITE_RULE`, never through a `SAVE_SETTINGS` patch, so an old tab cannot overwrite newer rules (V18).
- User data (hostnames, mode names) set with `textContent` only; no `innerHTML`. The pill stays in its closed Shadow DOM.
- Pages follow `prefers-color-scheme` with the tokens in `src/ui/base.css`, keep visible focus rings and keyboard order, no font under 12 px, text at 4.5:1, no sideways scroll at 380 px.
- A section's `render` never writes a focused field.
- No em or en dashes anywhere. In files the author is K. S. Karakostas.
- No version bump, no `CHANGELOG.md` heading.
- Commit messages carry the change description only: no trailers, no AI attribution.
- Every task ends with `npm test` green (report `N/N`) and `npm run build` clean; Task 6 also runs `npm run test:e2e`.
- One test file: `npx vitest run <path>`.

## Decisions this plan applies

K. S. Karakostas, 2026-11-04 (AskUserQuestion):
- Add site is a form: host input, Hide pill checkbox (on by default), Mode select, Add button. Nothing is stored until Add.
- Text typed in Add site and not confirmed stays a draft. Only Add or Enter stores a rule; nothing is added on blur, hide or close.

PROPOSED (controller, within the spec):
- `SET_SITE_MODE` may create a rule. The controller sends it only on a site with a mode rule (V9); a rule removed a moment ago elsewhere is then re-created by one click, which is harmless and needs no guard.
- `ruleFor` also maps a mode that no longer exists to `null`, so a stale rule never reaches the recorder.
- A hidden site that shows a status shows today's pill with it (spec V10: "statuses still shown"; L5 moves them to Minimal).
- The first idle pill waits for the first `GET_SETTINGS` answer, so a hidden site never flashes one. If that read fails the pill behaves as today (fail open: a visible pill is the safe side).
- `siteKey` strips one trailing dot, refuses a bare input with `@` before the first `/`, and detects a scheme only at the start of the input. `tel:123` still reads as host `tel`, port 123 (indistinguishable from `localhost:123`); the rule is harmless.
- The Web Store has no content scripts, so `pageSite` returns null there and the popup says "Not available on this page". The Sites page does not refuse those hosts: such a rule does nothing.
- A Sites row whose last setting is cleared is deleted (spec: an empty rule is deleted); focus moves to the next row's Remove button, else to the Add site input.
- Remove on the Sites page acts at once, with no inline confirm: a rule is cheap to re-add.
- `.item-tag` is added to `src/content/pill.css` (L5 owns that file, but the marking needs a style) and is append-only.

## Review Focus

1. A page that autofocuses a field, or a click into a field while the first `GET_SETTINGS` is on its way, on a hidden site. Expected: no pill at any moment. Pinned in Task 3 ("no pill before the first settings answer").
2. `GET_SETTINGS` fails at boot. Expected: the pill shows as today. Pinned in Task 3 ("a failed first read shows the pill").
3. A custom mode used by a rule is deleted, or a hand-edited rule names a missing mode. Expected: dictation uses the active mode, the pill shows no "This site". Pinned in Task 1 ("a missing mode reads as null") and Task 2 ("a stale site mode falls back to the active mode").
4. Odd Add site input: `mailto:a@b.com`, `user:pw@evil.com`, `https://WWW.Example.COM./x`, `example.com/login?next=https://x.com`, `__proto__`, a Greek IDN. Expected: refused or normalized to the host the tab reports; no prototype touched. Pinned in Task 1 (table test) and Task 5 ("refuses input that is not a host").
5. The popup with settings not loaded, or two quick edits before the re-read. Expected: no rule written from fallback settings; the second edit keeps the first. Pinned in Task 4 ("never writes a rule from unloaded settings", "a second quick edit keeps the first").
