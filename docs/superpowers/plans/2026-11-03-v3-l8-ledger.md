## Streaming: measured (Atlas, 2026-11-05)

Question: roadmap 7.1 sets `stream=true` on the transcriptions endpoint, and VoiceType uploads a finished recording. Does streaming bring text sooner, and can the worker read it?

Rig: live `api.openai.com`, model `gpt-transcribe`, from K. S. Karakostas's machine and network. Speech is OpenAI TTS (`gpt-4o-mini-tts`, one voice), passed through a real Chrome 156 `MediaRecorder` with the shipped options (`audio/webm;codecs=opus`, 32 kbps), so the bytes have the shape the extension uploads. Sentences are plain dictation. Each recording ran 5 pairs of batch and stream, order alternating. Row labels give the speech length; the uploaded files run 7.6, 24.5, 31.7 and 54.1 s, with the 0.8 s of silence the recording adds. Times are ms from the request start to the event, median [min, max]. No language or keyword hints. The service worker row group is a real MV3 worker in Google Chrome 156.0.8078.79, headed in a nested X display, loaded with one `Extensions.loadUnpacked` on `--remote-debugging-pipe` and no target session, so no DevTools held it.

Answers:
- `gpt-transcribe` streams: `stream=true` gives HTTP 200, `text/event-stream`, `transcript.text.delta` per word or so, then `transcript.text.done` carrying the full `text`, `usage` and `languages`. 20/20 in Node and 20/20 in the worker. The joined deltas equal the final text in every stream.
- A Chrome 156 service worker reads it: `res.body.getReader()` gave 2 to 159 separate reads, spread over the same window as in Node, so nothing buffers it.
- Deltas start only after the whole file is in: the premise of the kickoff holds. A multipart body paced over the speech length got no delta until the upload ended.

What this means:
- Streaming shows the first word 0.1 s to 0.85 s sooner than the batch result (paired medians), and the final text no sooner: paired final differences are -71 to +12 ms. All of it happens after the user stops talking; nothing appears while speaking.
- The whole transcript is on the wire 0.1 s to 0.9 s after the first word. A ghost text would flash and be replaced.
- In a mode with a prompt, the raw transcript sits unseen for 2 to 4 s while the text model runs. Showing it needs no streaming and works on both providers. Not in the roadmap; PROPOSED as an alternative.

Limits of the sample: synthetic speech, one voice; one network, with a fast uplink, so a slow uplink's upload time is not in these numbers and it would delay both arms alike; 5 pairs; Chrome 156 only; no hints sent; the numbers start at the request, so the offscreen stop and the base64 step are not in them. The batch outlier of 3900 ms is left in. One of the 10 Node calls on the 53.4 s recording, a batch one, returned a transcript with one comma more; the Node texts of the other recordings all agreed. The worker rows kept lengths only.

Spend: about 50 minutes of audio at list price plus TTS and six refines, under USD 0.50 (estimate from `usage` and the model table, not read from a bill).

## Worker lifetime: a correction to the L7 ledger

The first worker run stopped dead about 30 s in, after the 27th call of 42, during the 28th, on a healthy network. Bare probes, Chrome 156, no DevTools, a local server answering after 45 s:

| Arm | What the worker has open | Outcome |
|---|---|---|
| Fetch only, 5 s timers | The fetch | dropped at 30.0 s from the last event |
| Fetch, an idle offscreen document | The fetch | dropped at 30.0 s |
| Fetch inside an open reply to an offscreen `sendMessage` | The fetch, the reply | lived, body read at 45.0 s, timers ran on |

- A fetch in flight does not hold a worker, and neither do timers. The L7 ledger's "likely candidate is the fetch in flight" (ASSUMED, not tested) is wrong in a bare worker. One run each.
- An open message reply does hold it. In the shipped build the reply to `OFFSCREEN_DONE` stays open for the whole provider call (`router.js`, `await recorder.onDone`), so 3.1's measured result stands.
- L7's last row (a scratch build replying to `OFFSCREEN_DONE` at once still landed) means something else also held that worker. Not traced.
- Rule for this lane: long work in the worker hangs off an open reply or makes extension API calls. A stream that sends deltas to a tab does. Traps entry when `docs/TRAPS.md` exists; none does yet.

## Worker crash: measured (Atlas, 2026-11-05)

Rig as in "Worker lifetime", plus `--no-sandbox` and a CDP session for the stop or the crash: a probe extension, a local server answering after 30 s, a content script pinging every 2 s, an open reply holding the worker. 1.5 MB in `chrome.storage.session`. `.superpowers/smoke/crash/`.

| Arm | Browser | Worker | Offscreen document | `storage.session` | Page |
|---|---|---|---|---|---|
| `ServiceWorker.stopAllWorkers` | Chrome 156 | fetch dropped at once; a new worker answered the next ping within 100 ms | still there | 1.5 MB intact | pings went on |
| `Page.crash` on the offscreen document, same process as the worker | Chrome 156, 2 runs | gone, 3.4 to 3.6 s later | gone | not readable | "Could not establish connection" twice, then "Extension context invalidated" |
| Same | Chrome for Testing 140, 1 run | gone in 0.2 s | gone | not readable | "Could not establish connection" |

- A process crash takes the worker and the offscreen document together and the content script's context goes invalid. A new page opened 8 s later had no content script for the 10 s watched (Chrome 156 only). Nothing inside the extension is left to retry, and the audio is gone. Chrome's later reload of the extension, if any, was not watched past those 10 s.
- A stopped worker with the process alive is recoverable. No natural trigger for that stop has been seen: L7's 45 s arms were not stopped, and the 5 minute event limit is past the 60 s request limit.

Pings alone: the bare probe with a 50 s fetch, no open reply, a content script messaging every 5 s: the body arrived at 50.0 s on Chrome 156 and on Chrome for Testing 140, one run each (`runhold.mjs`). So a resumed run needs no other hold.

## Spec check (2026-11-05)

A fresh reader planned from the spec. Settled by Atlas, tagged PROPOSED in the spec, for K. S. Karakostas to overrule:
- An alive ping re-arms the 75 s watchdog (V52). Why: a retry of up to 60 s would otherwise show a false error, then end the pings.
- A failed ping tests `isAlive`, and the bound is about 10 s (V52). Why: Chrome 156 took 3.6 s to invalidate the context, and the Chrome 140 run recorded only the connection error.
- A record nobody pings for is swept by the next worker start or message, with no alarm (V53). Why: `alarms` would be a new permission.
- A start no longer waits for a pending retry; it clears the record (V53). Simplified from a refusal that could block every tab for 120 s for a page already gone.
- A contenteditable's check is text and offsets (V47). Why: same text alone would overwrite the same word elsewhere, against the anti-goal.
- A failed edit's status is not sticky (V46). Why: a sticky one turns the retry press into a copy over the clipboard, and an instruction is not worth that.
- A resumed run adds no history entry (V52). Why: the clear count is in memory, so a Clear before the stop would be forgotten, against V27.
- V50's browsers corrected: e2e runs Chromium 153, not Chrome 156; Chrome 156 is the harness. V57 needs `VT_CHROME_BIN` in `test/e2e/helpers.js`.
