## Step A: platform verification (V6)

Docs read 2026-11-03:
- developer.chrome.com/docs/extensions/reference/api/runtime: `getContexts(filter)` Chrome 116+; `ContextType` includes `TAB`; `ExtensionContext` has `tabId`, `windowId`, `documentUrl` (-1 / undefined when not in a tab or document); "Most members of this API do not require any permissions" (only native messaging does). `openOptionsPage` "will never cause the caller page to reload" and may focus an open options page.
- /reference/api/tabs: the `tabs` permission "does not give access to the chrome.tabs namespace"; it only exposes `url`, `pendingUrl`, `title`, `favIconUrl`. "Most features don't require any permissions", navigating tabs included. `update` `url`: "JavaScript URLs are not supported".
- /reference/api/windows: no permission listed for `windows.update`; `focused: true` "brings the window to the front".
- /develop/ui/options-page: `open_in_tab` "Indicates whether the extension's options page will be opened in a new tab"; embedded options (false) cannot use the Tabs API. No mention of URL fragments.

Probe, headless Chromium 153.0.8010.12 through Playwright, a throwaway extension with `options_ui: { page: "options.html", open_in_tab: true }`, permissions `["storage"]` only (no `tabs`), the route code run from `popup.html` opened as a tab:
1. No settings tab open: `tabs.create({ url: options.html#home })` opened it; one load.
2. `getContexts({ contextTypes: ['TAB'] })` returned both extension tabs (popup.html in its tab, options.html) with `tabId`, `windowId`, `documentUrl`; `documentUrl` carries the hash (`.../options.html#home`).
3. `getContexts({ contextTypes: ['TAB'], documentUrls: [<options.html without hash>] })` returned 0 contexts: the filter is an exact match, so the page must be found by comparing `documentUrl` without its fragment.
4. `tabs.update(tabId, { active: true, url: options.html#settings/provider })` and `windows.update(windowId, { focused: true })`: no error; the tab became the active tab; a same-document navigation (a `window` marker survived, load count stayed 1, one `hashchange`).
5. The same call with the hash the tab already shows: no reload, no `hashchange`.
6. `runtime.openOptionsPage()` with the tab open: no new tab, no reload, the hash kept.

Result: V6 holds without the `tabs` permission. VERIFIED (probe output above). Not verified: window focus across real OS windows (headless), and the call from a real action popup rather than popup.html in a tab (same extension-page API surface; the L0 smoke checks it).

Consequences for the plan: the popup finds the settings tab by `documentUrl.split('#')[0] === chrome.runtime.getURL('options.html')`, never with the `documentUrls` filter, and never matches its own `popup.html` tab.

## Decisions (K. S. Karakostas, 2026-11-03, AskUserQuestion)

- Q1 "Open settings" in the popup: focus an open settings tab as it is (no route change); with none open, create one at `#home`. "Add API key" opens `#settings/provider`.
- Q2 Default route with no or an unknown hash: `#home` (a placeholder until L1).
- Q3 Reset to defaults (V21) as specified; custom modes are deleted as in 2.2, so site rules that use one lose their mode (a mode-only rule is deleted). The confirm prompt and hint say so.

## Rulings during planning (PROPOSED, within the spec)

- The popup Esc workaround goes: the slim popup has no text fields, and in a settings tab Esc closes nothing.
- Settings-page text fields debounce 400 ms (spec 4.1); the popup's 800 ms goes with the popup's text fields.
- Dictionary validation (spec 4): unknown group codes dropped; terms trimmed, empty ones dropped; case-insensitive duplicates across groups dropped, first in display order kept (V20); total capped at 100 in display order; an empty group is kept (L2's page may hold one). A v2 store with no keywords migrates to `dictionary: {}`.
- Site-rule validation: keys normalized with `siteKey`; an invalid key dropped; two keys that normalize alike keep the first; `hidePill` non-boolean becomes `false`.
- The vocabulary textarea in Settings, Speech edits `dictionary.any` and skips terms already in another group, so the service worker's dedupe never moves a term between groups.
