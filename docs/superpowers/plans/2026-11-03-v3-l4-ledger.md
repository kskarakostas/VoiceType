## Step A: spikes (spec 6.5)

Harness: a throwaway extension with the real document shape (offscreen document created by the service worker, no user gesture anywhere), Playwright, session scratchpad `spike/`. Browsers: Chromium 153.0.8010.12 headless and headed, Google Chrome 156.0.8078.79 headed (branded Chrome ignores `--load-extension`; loaded through CDP `Extensions.loadUnpacked` with `--enable-unsafe-extension-debugging`). Headed runs used a nested Xephyr display with its own X clipboard. Audio went to a throwaway PipeWire null sink set per process with `PULSE_SINK` and `PULSE_SOURCE`; the default devices were not changed and the sink was removed afterwards.

### (a) A cue from the offscreen document

Offscreen document with `reasons: ['USER_MEDIA', 'CLIPBOARD']`, no `AUDIO_PLAYBACK`, no gesture (`navigator.userActivation.hasBeenActive` false). Output captured with `parec` from the sink monitor.

| Browser | Case | `AudioContext` state | Peak RMS of the output |
|---|---|---|---|
| Chromium 153 headless and headed | first cue in a new document, same context, new context | `running` before `resume()` | 0.2126 to 0.2127 (160 to 180 ms) |
| Chrome 156 headed | same | `running` | 0.2086 to 0.2087 |
| Chrome 156 headed | after 45 s idle; document still alive | `running` | 0.2086 |
| Chromium 153 and Chrome 156 with `--mute-audio` (control) | same | `running` | 0 |

A 0.3 gain sine has RMS 0.212, so the level is right. The control shows that `AudioContext.state` alone proves nothing: a muted browser also reports `running`. Harness check: a known tone through `paplay` read 0.2127.

Result: PASS. V13 holds, the cue plays from the offscreen document. VERIFIED. `AUDIO_PLAYBACK` stays out of the recording document.

### (b) `execCommand('copy')` in the offscreen document while a page has focus

The page held focus and a caret in a textarea; the clipboard was seeded with `SEED` through a real Ctrl+C. Read back with Ctrl+V and, headed, with `xclip` on the real X clipboard.

| Browser | Manifest | Reasons | `execCommand` | Clipboard after |
|---|---|---|---|---|
| Chromium 153 headless and headed, Chrome 156 headed | no `clipboardWrite` | `USER_MEDIA`, `CLIPBOARD` | `false` | `SEED` |
| Chromium 153 headless and headed, Chrome 156 headed | `clipboardWrite` | `USER_MEDIA`, `CLIPBOARD` | `true` | the text |
| Chromium 153 headed | `clipboardWrite` | `USER_MEDIA` only | `true` | the text |

Page focus, caret and selection did not change in any run. `navigator.clipboard.writeText` from the document rejects in every case ("Document is not focused"). `execCommand` returned `true` with `clipboardWrite` and nothing selected, and wrote nothing: its return value alone is not proof.

Result: FAIL as specified. V12 assumed no new permission. The `CLIPBOARD` reason does not grant the write; the `clipboardWrite` permission does. Doc: permission warning "Modify data you copy and paste." (developer.chrome.com/docs/extensions/reference/permissions-list).

A `copy` listener that supplies the text, with no selection and no textarea, in the document with `clipboardWrite`: `ran` and `supplied` true, clipboard exact for multi-line Greek, leading spaces and 200,000 characters (Chromium 153 headless). It adds a real success signal, so L4 uses it instead of a textarea.

Alternative tested: a content script with no new permission, the two rungs of `copyText`, Chromium 153 headed, real X clipboard:

| Case | Activation expired (over 5 s) | Fresh activation | `clipboardWrite`, activation expired |
|---|---|---|---|
| top field | no, pending | yes | yes |
| cross-origin iframe, the iframe copies | no | yes | yes |
| cross-origin iframe, the top frame copies | no, pending | yes | yes |
| iframe with `allow="clipboard-write"` | no | yes | yes |
| tab in the background | no, pending | yes (the click brought it to the front) | yes |
| back in front | no, pending | yes | yes |
| plain http (not a secure context) | no | yes | yes |
| `Permissions-Policy: clipboard-write=()` | no | yes | yes |

Hold to talk and silence stop end long after the last user action, so a content-script copy would fail on the common paths. "pending" is the defect below.

### (c) Does a start cue reach the transcript?

Real `getUserMedia` with the extension's constraints, the mic being the sink monitor: the cue arrives at full level with no acoustic loss. Real `MediaRecorder` output sent to `gpt-transcribe` and `gemini-3.5-transcribe`. 880 Hz, 120 ms, gain 0.3, four rounds.

| Case | Peak RMS in the recording | OpenAI | Gemini |
|---|---|---|---|
| silence, no cue | 0 | empty | empty |
| cue right after capture starts, AEC on | 0.0011 to 0.0185 | empty | empty |
| cue before capture | 0 | empty | empty |
| cue after capture, AEC off (control) | 0.213 | empty | empty |

Control: with AEC off the cue is in the recording at full level, so the harness shows a leak. Even then neither provider returned text. Two speech runs (one TTS sentence through `paplay`, which is not Chrome's output, so AEC does not remove it): each cue placement returned the full sentence from both providers. The only text differences were in how the time was written ("at 10", "at ten", "at 10:00").

Result: PASS. The cue does not reach the transcript. An empty transcript shows "No speech detected." as the spec expects. VERIFIED for a digital loop, in the worst case for level. Not verified: real speakers and a real microphone in a room (TO CONFIRM, K. S. Karakostas).

### Defect found: a clipboard write can stall a paid transcript

Present in released 2.2.0 (`git show main:src/content/insert.js`). With no user activation, `navigator.clipboard.writeText` in a focused document opens a permission prompt attributed to the web page ("wants to See text and images copied to the clipboard") and the promise stays pending until the user answers. `copyText` awaits it (`src/content/insert.js:72`).

Reproduced on the real build, headed, stubbed provider with an 8 s delay: REC, stop, click another field, so D12 sends the text to the clipboard.
- As built: the prompt shows, the pill stays on its processing state, no status at 6.5, 9.5, 11.5 and 15 s, the clipboard unchanged.
- The same build with `clipboardWrite` added: "The field lost focus. Text copied to clipboard." and the text on the clipboard.

Reached by: the focus-moved path with a slow provider; every `copyAs` rung in `insertText` (`docs.google.com` always) when the last user action is over 5 s old, for instance hold to talk.
